# Core Infrastructure

## Назначение

Директория `core/` содержит **базовую инфраструктуру сервера**, которая является фундаментом для всех остальных сервисов и проектов.

`core` — это минимальный, обязательный слой, без которого:

* невозможно корректно развернуть сервисы приложений,
* невозможно обеспечить единый вход (HTTP/HTTPS),
* невозможно централизованно управлять инфраструктурой.

Вся инфраструктура в `core/` поднимается **как код (IaC)** и может быть воспроизведена на новой виртуальной машине после выполнения bootstrap-этапа.

---

## Что входит в core

На текущем этапе `core` включает следующие сервисы:

### 1. Reverse Proxy (Caddy)

Роль:

* единая точка входа в инфраструктуру по HTTP/HTTPS;
* маршрутизация запросов по доменным именам;
* изоляция внутренних сервисов от прямого доступа.

Характеристики:

* слушает порт **80** (позже 443);
* проксирует запросы во внутреннюю Docker-сеть;
* конфигурация хранится в виде кода (`Caddyfile`).

### 2. Gitea

Роль:

* собственный Git-сервер для инфраструктуры и проектов;
* источник истины для IaC-репозиториев;
* работа исключительно внутри локальной сети.

Характеристики:

* доступна через reverse proxy по домену `gitea.tond.local`;
* SSH-доступ для git по отдельному порту;
* все данные хранятся в именованных Docker volumes.

---

## Архитектурные принципы core

В `core` зафиксированы следующие правила:

* **Infrastructure as Code** — всё описано в файлах и скриптах;
* **Один вход** — наружу смотрит только reverse proxy;
* **Нет IP-адресов** — сервисы общаются по именам контейнеров;
* **Явные имена** — Docker networks и volumes именуются явно;
* **Без секретов** — `core/.env.core` не содержит чувствительных данных;
* **Идемпотентность** — повторный запуск не ломает систему.

## Структура директории

```text
core/
├── .env.core              # Общие константы core-инфраструктуры (без секретов)
├── core.up.sh             # Основной скрипт запуска core
├── core.check.sh          # (планируется) Общая проверка core-сервисов
│
├── proxy/
│   ├── docker-compose.yml # Reverse proxy (Caddy)
│   ├── Caddyfile          # Маршрутизация доменов
│   └── proxy.check.sh     # Проверка proxy
│
├── gitea/
│   ├── docker-compose.yml # Git-сервер
│   ├── .env.example       # Локальная конфигурация сервиса (минимум)
│   └── gitea.check.sh     # (планируется) Проверка Gitea
│
└── README.md              # Этот файл
```

## Зависимости

Перед запуском `core` **обязательно** должен быть выполнен bootstrap-этап.

Bootstrap обеспечивает:

* установленный Docker;
* установленный Docker Compose plugin;
* базовую настройку системы;
* firewall и базовую безопасность.

Без bootstrap запуск `core` **не поддерживается**.

---

## Как запустить core

### 1. Подготовка

Убедитесь, что:

* вы находитесь на сервере;
* bootstrap выполнен;
* файл `core/.env.core` создан и заполнен.

### 2. Запуск

```bash
cd core
chmod +x core.up.sh
./core.up.sh
```

Скрипт:

* загрузит `.env.core`;
* создаст Docker-сеть (если нужно);
* проверит конфигурацию proxy;
* поднимет reverse proxy;
* поднимет Gitea.

### 3. Проверка

После запуска рекомендуется выполнить:

```bash
cd proxy
./proxy.check.sh
```

---

## Что core НЕ делает

Важно понимать границы ответственности:

`core` **НЕ**:

* разворачивает бизнес-приложения;
* содержит CI/CD пайплайны;
* управляет секретами;
* настраивает облачные провайдеры;
* заменяет bootstrap.

`core` — это фундамент, а не всё здание.

---

## Итог

Если:

* сервер можно снести;
* развернуть заново;
* выполнить bootstrap;
* запустить `core.up.sh`;
* и получить рабочий Git + proxy,

значит core-инфраструктура реализована корректно.

Это и есть цель данного этапа.
